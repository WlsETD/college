## 3.1 角色

三種角色，記錄在 `groups/{gid}.roles`（型別 `Record<uid, 'owner' | 'admin' | 'viewer'>`）。
這是權限判斷的**單一來源**，安全規則只讀這個欄位。

| 角色 | 中文 | 說明 |
| --- | --- | --- |
| `owner` | 擁有者 | 建立群組的人。同一個群組只有一位。 |
| `admin` | 管理者 | 由擁有者指派。可維護所有課程內容。 |
| `viewer` | 檢視者 | 透過邀請連結加入的預設角色。唯讀。 |
| — | 非成員 | 未在 `roles` 中的登入使用者。 |

`owner` 與 `admin` 合稱**管理者權限**（`isManager`）。

## 3.3 逐條說明與取捨

**移除成員。** 管理者可以移除檢視者，但不能移除其他管理者——只有擁有者能動管理者。
這是 2026-09-22 從草案放寬的一項：班級情境下退選、轉班很常見，
每次都要找擁有者處理太麻煩。

**擁有者不能自行退出群組。** 必須先把擁有者轉移給別人才能退出，
否則群組會變成無主狀態，沒有人能再指派管理者。

**復原開放給管理者。** 把 `deletedAt` 改回 `null` 是允許的，對象是擁有者與管理者。
嚴格來說這讓「軟刪除」不是單向操作，但班級共用的情境下誤刪很常見，
保留復原路徑比維持形式上的單向性實用。檢視者無此權限。

**Storage 物件一律不可刪除。** 檔案的「刪除」只是把對應的 `item` 軟刪除，
實體檔案保留在 Storage。長期會累積孤兒檔案，之後以排程 Function
清理軟刪除超過 N 天的物件——那是階段二的工作。

**邀請文件完全不經前端。** `invites` 子集合的讀寫一律拒絕，
只由 Cloud Functions 以 Admin SDK 存取。原因是非成員無法通過安全規則
寫入 `groups/{gid}.roles`，所以「用邀請連結加入」這個動作一定要走後端。

## 3.4 安全規則的判斷邏輯

```
roleOf(gid)    = get(/databases/$(db)/documents/groups/$(gid)).data.roles[request.auth.uid]
isSignedIn()   = request.auth != null
isMember(gid)  = isSignedIn() && roleOf(gid) != null
isManager(gid) = roleOf(gid) in ['admin', 'owner']
isOwner(gid)   = roleOf(gid) == 'owner'
isSelf(uid)    = request.auth.uid == uid
notDeleted()   = resource.data.deletedAt == null
```

適用規則：

- **讀取**：`isMember(gid) && notDeleted()`
- **建立／編輯內容**：`isManager(gid)`
- **`delete` 動作**：一律 `if false`
- **軟刪除**：`update`，且 `deletedAt` 由 `null` 變成 `request.time`
- **復原**：`update`，且 `deletedAt` 由非 `null` 變成 `null`，需 `isManager(gid)`
- **`roles` 與 `ownerUid` 欄位**：`isOwner(gid)`。
  轉移擁有者必須在**同一次 update** 內同時修改 `ownerUid` 與 `roles`，
  且新擁有者原本已是成員。
- **移除檢視者**：`isManager(gid)`，且被移除者的原角色為 `viewer`
- **`members/{uid}.enrolledSubjectIds`**：`isSelf(uid)`

### 兩個實作上的陷阱

**一、`notDeleted()` 在 list 查詢會整個被拒。**
安全規則不會替你過濾資料。只要查詢的結果集裡**可能**包含 `deletedAt` 不為 `null` 的文件，
整個查詢就會 permission-denied，而不是把那幾筆濾掉。
因此前端每一個查詢都必須自己帶 `where('deletedAt', '==', null)`，
且 `firestore.indexes.json` 的每個複合索引都要含 `deletedAt`。

**二、App Check 的強制不寫在規則裡。**
`request.app` 在 Emulator 中不受支援，寫進規則會讓規則測試整批失敗。
在 Firebase Console 對 Firestore 與 Storage 分別開啟 enforcement，
Cloud Functions 用 `enforceAppCheck: true`。

## 3.5 檢視者的可見範圍

安全規則讓檢視者讀得到**整個群組**的資料，「我修的科目」只在前端過濾。

若要在規則層真正擋住未選的科目，每次讀取都得額外 `get()` 該成員的
`enrolledSubjectIds` 並逐科目比對，讀取成本與規則複雜度都會明顯上升。
以班級共用課程進度這個情境來說，同班同學本來就看得到彼此的課表，
不構成實質的隱私問題。

## 3.6 測試要求

`@firebase/rules-unit-testing` 搭配 Firebase Emulator，
**權限表的每一格都要有對應的測試案例**——標 ✓ 的寫「允許」測試，
標 ✗ 的寫「拒絕」測試。預估約 100 個案例。

Storage 的四個條件（成員身分、管理者身分、30 MB 上限、拒絕 `video/*`）
各自都要有獨立的拒絕案例，不能只測聯集。
